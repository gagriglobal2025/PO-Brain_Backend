## Project Overview

PO-Brain is an AI-powered Purchase Order extraction and monitoring system. It automatically polls a Gmail inbox for emails containing PO data (in email body or PDF attachments), extracts structured data using OpenAI GPT-4o, stores it in a SQL Server database, and surfaces it through a React dashboard.

The repo has three independent sub-projects:
- **`Extraction_file/`** — Python pipeline (the core engine)
- **`Backend/`** — .NET 8 Web API (C#, in progress)
- **`Web/PO-Brain/`** — React/TypeScript frontend dashboard

## Extraction Pipeline (Python)

### Setup
```bash
cd Extraction_file
pip install -r requirements.txt
```

Tesseract OCR is optional but required for scanned PDFs. On Windows, install from the Tesseract installer and set `TESSERACT_PATH` in the `CONFIG` dict inside the script.

### Run modes
```bash
# Continuous polling (default — runs forever, polls every 120s)
python unified_po_extractor.py

# Single test cycle then exit
python unified_po_extractor.py --once

# Test a single .eml file
python unified_po_extractor.py --file email.eml

# Verify database connectivity
python unified_po_extractor.py --test-db

# Verbose debug output
python unified_po_extractor.py --debug
```

`unified_po_extractor.py` is the current production extractor — it handles both PDF attachments and plain/HTML email body text and writes to the normalized `dbo.pobrain_*` schema. `index.py` and `po_extractor.py` are older versions (v1/v3) that target a flat `dbo.email_purchase_orders` table and use a local `processed_emails.txt` file for deduplication instead of IMAP flags.

### Key configuration
All credentials are hardcoded in a `CONFIG` dict at the top of each script. The PRD flags this as a known issue — environment variables are a planned improvement.

## Frontend (React/TypeScript)

All commands run from `Web/PO-Brain/`.

```bash
npm install        # or: bun install
npm run dev        # dev server on http://localhost:8080 (opens browser)
npm run build      # production build to dist/
npm run lint       # eslint check
npm run test       # vitest run (single pass)
npm run test:watch # vitest in watch mode
```

The app is served under the `/Pobrain/` base path (set in `vite.config.ts`). The dev server runs on port **8080**, not the default 5173.

### Architecture

- **Routing**: `BrowserRouter` with `basename="/Pobrain/"`. Protected routes use `AdminLayout` (sidebar + topbar shell via React Router `<Outlet>`). The login page is outside the layout.
- **Layout**: `AdminLayout` wraps all authenticated pages with `AppSidebar` (collapsible icon sidebar) and a sticky top header with breadcrumbs, notifications, and a user dropdown.
- **Pages**: `Dashboard`, `ExtractionResults`, `ProcessingLogs`, `FailedTransactions`. `DataPreview` is commented out/in progress.
- **UI components**: All in `src/components/ui/` — these are shadcn/ui primitives generated by the component registry. Do not edit them directly; add new ones with the shadcn CLI.
- **Path alias**: `@/` resolves to `src/`.
- **State**: No global state library — TanStack Query (`@tanstack/react-query`) is wired up in `App.tsx` but not yet used for data fetching (pages currently use hardcoded mock data).

## Backend (.NET 8 API)

The backend is a single-project ASP.NET Core Web API in `Backend/`. It uses EF Core 8 with SQL Server, Serilog for structured logging (console + rolling file at `logs/pobrain-.log`), SignalR for real-time log streaming, and Swagger/OpenAPI.

CORS is configured to allow `http://localhost:3000` and `http://localhost:5173`.

```bash
cd Backend
dotnet run
dotnet build
dotnet test   # no test project exists yet
```

## Database

Scripts in `Database/` must be run in order against **`hyma_testdb`** on `3.109.43.10:8016`:

```
01_create_tables.sql   — All 16 dbo.pobrain_* tables
02_foreign_keys.sql    — FK constraints
03_indexes.sql         — Performance indexes
04_seed_data.sql       — Reference/lookup data
05_views_dashboard.sql — Dashboard views
06_sample_data.sql     — Sample rows for development
```

### Schema structure (`dbo.pobrain_*` prefix, 3NF)

| Group | Tables |
|---|---|
| Lookup/reference | `lkp_status`, `lkp_log_level`, `lkp_processing_stage`, `lkp_error_category`, `lkp_parsing_engine` |
| Core transactions | `emails`, `email_attachments`, `extraction_jobs`, `purchase_orders`, `purchase_order_line_items` |
| Monitoring/ops | `workflow_steps`, `processing_logs`, `error_logs`, `failed_transactions`, `audit_logs`, `system_health_snapshots` |

The Python `unified_po_extractor.py` writes to this normalized schema. The older scripts (`index.py`, `po_extractor.py`) write to the legacy flat table `dbo.email_purchase_orders` on a different server (`198.38.84.193:1234`, database `GG26_GagriLearning`).

## Data Flow

```
Gmail IMAP (UNSEEN emails)
  → Parse email body (plain text + HTML via BeautifulSoup)
  → If PDF attached: pdfplumber (native) → pytesseract OCR (fallback)
  → OpenAI GPT-4o: returns JSON array, one object per line item
  → SQL Server: insert into pobrain_emails → attachments → extraction_jobs
                → purchase_orders → purchase_order_line_items
                + workflow_steps, processing_logs, audit_logs
  → Move email to 'processed' or 'failed' IMAP folder
```

The AI always returns a JSON **array** (one dict per product row). Fields shared across all line items (PO number, date, address, GST numbers) are repeated in every object. `unified_po_extractor.py` then normalises this into the relational schema.
